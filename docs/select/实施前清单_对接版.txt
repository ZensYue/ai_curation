KP电子产品自动选品项目实施前清单

说明
这份清单用于项目启动前的资料准备与问题确认。先把资料补齐，再开始搭建流程，可以明显减少后续返工。

一、需要提供的资料

1. 平台与账号资料
KP 平台名称、网址、登录方式、是否有 API。
Vika 的 API Token、空间信息、目标表信息、是否已建表。
国内平台可用方式：API、网页抓取、榜单页或搜索页。
欧洲平台首批名单及访问入口。
汇率接口来源。
ePonuda 或其他塞尔维亚比价网站的入口与可用方式。

2. 数据源清单
KP 热卖榜入口 URL。
欧洲热卖平台 URL。
国内热卖榜 URL。
新品监控来源。
每个平台的目标类目范围。

建议先明确的新品来源：
品牌官网，用于捕捉新品发布、参数和官方定价。
科技媒体，用于补充新品发布时间、市场关注度和链接。
RSS 源，用于自动监控更新，降低人工检查成本。

3. Vika 表结构资料
每张表最终名称。
每张表字段名与字段类型。
唯一键规则。
更新策略，明确是覆盖更新还是追加历史。
是否需要主看板汇总表。

4. 商品标准化资料
品类字典。
品牌别名映射。
型号命名规则。
去重规则。

建议首期标准品类：
手机。
大相机。
小相机或运动相机。
电脑设备。
配件。
其他电子产品。

5. 业务判定规则
热卖前 50 的具体榜单定义。
浏览量、收藏数、销量、评价增量的可获取性。
热门关注商品的判定阈值。
可降价切入商品的判定阈值。
增量商品的判定阈值。
蓝海产品的判定阈值。
最低利润额和利润率门槛。

6. 成本与物流资料
国内采购成本取值规则。
头程参数是否固定。
尾程费用规则是否按文档默认表。
是否有特殊品类附加费。
汇率刷新频率。

文档默认参数：
空运单价为 69 RMB/KG。
体积重基数为 6000。
最低计费重为 12KG。

7. 环境与风控资料
是否已有当地代理 IP。
是否允许浏览器自动化。
是否需要验证码处理。
n8n 运行环境。
告警渠道。

建议明确的运行环境：
本地。
云端。
Docker。

建议明确的告警渠道：
Telegram。
邮件。
飞书或钉钉。

二、需要回答的问题

1. 数据源与抓取方式
KP 平台是否只能网页抓取？
KP 热卖榜按什么维度获取？
欧洲首批做哪些国家、哪些站点？
国内平台价格抓取用什么口径？
新品监控首期做哪些固定来源？

2. 商品标准化与映射
型号标准化靠规则表、AI，还是两者结合？
品牌一致加型号一致是否足够作为去重规则？
颜色、容量、套餐是否算同款？
平台标题混乱时是否允许人工维护映射表？

3. 业务规则与判定标准
浏览量、收藏数、近 7 天新增评价是否都能拿到？
拿不到时是否允许用替代指标？
蓝海产品中的 KP 供应稀缺或热度不高如何定义？
最低利润额和利润率门槛是多少？
哪些商品类型需要直接剔除？

4. 成本、汇率与本地比价
国内采购成本按标价、到手价还是最低采购价？
ePonuda 搜不到商品时是否继续利润核算？
尾程费用是否按国家拆分？
汇率取实时值、每日值还是人工维护值？

5. 数据回写与业务使用
Vika 是多表管理，还是主表加明细表？
是否需要人工确认状态字段？
候选品跟进状态是否先只保留三档？
是否需要保留抓取历史和利润历史？

三、建议先固定的表

KP平台产品热卖信息。
周边国家热卖产品信息。
国内产品热卖信息。
国内新发布产品信息。
有潜力产品信息表。
选品利润核算表。
商品映射规则表。
全局参数表。

四、建议实施顺序

第一步，先确认平台与账号资料。
第二步，先定 Vika 表结构。
第三步，再定商品标准化与去重规则。
第四步，再定潜力筛选阈值。
第五步，再定利润核算参数。
第六步，最后开始拆 n8n 流程并实施。
